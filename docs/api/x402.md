# x402 facilitator interface

The gateway serves the facilitator interface of [x402](https://www.x402.org/) v2 over HTTP. It uses the protocol's `batch-settlement` scheme on Stellar networks.

- A buyer's prepaid balance on the seller's ledger contract backs each paid request.
- The buyer authorizes each request with a **commitment**: a classic account signs it with its Stellar key, and a contract account, such as a passkey smart wallet, authorizes it through its own `__check_auth`.
- Settling a commitment debits the buyer at once. The value moves on-chain in the next charge batch.

A resource server, or a facilitator acting for it, calls this interface with the seller deployment's API key. It serves the resource once `/settle` succeeds.

Served when `PAY_STELLAR_X402_LISTEN_ADDR` is set (for example `0.0.0.0:8402`). It applies the same concurrency and time bounds as the gRPC API, and requests are limited to 16 KB. Contract-account buyers are served when `PAY_STELLAR_X402_VERIFIER_CONTRACT` names the [commitment verifier](#contract-account-payers).

## Endpoints

| Method and path | Authentication | Purpose |
|---|---|---|
| `GET /supported` | none | The scheme and network served, and in `extra.commitmentVerifier` the verifier contract-account buyers authorize against |
| `POST /verify` | `Authorization: Bearer <api key>` | Checks a commitment; debits nothing |
| `POST /settle` | same | Turns a commitment into a charge |
| `GET /settlements/{commitment}` | same | The charge a commitment became, and its on-chain transaction once it has landed |

`/verify` and `/settle` take the protocol's request body and answer with its response schemas, `VerifyResponse` and `SettleResponse`. A refusal is answered with HTTP 200 and a reason; a body that does not parse is answered with HTTP 400.

```json
{
  "x402Version": 2,
  "paymentPayload": {
    "x402Version": 2,
    "resource": { "url": "https://seller.example/api/answer" },
    "accepted": { ...the payment requirements the buyer accepted... },
    "payload": {
      "payer": "G...",
      "commitment": "64 lowercase hex characters",
      "validUntil": "1790000000",
      "signature": "base64 of 64 bytes"
    }
    (or, for a contract account: "payer": "C...", and in place of
     "signature", "authorizationEntry": "base64 of the signed entry's XDR")
  },
  "paymentRequirements": {
    "scheme": "batch-settlement",
    "network": "stellar:testnet",
    "amount": "50000",
    "asset": "C... (the USDC Stellar Asset Contract)",
    "payTo": "C... (the seller's prepaid ledger contract)",
    "maxTimeoutSeconds": 120
  }
}
```

`amount` is in USDC base units (7 decimals: `10000000` is 1 USDC).

## The `batch-settlement` binding on Stellar

### Commitment format

A classic account signs the following text with the key of its `payer` account, as a SEP-53 message: Ed25519 over `SHA-256("Stellar Signed Message:\n" || text)`. This is the form Stellar wallets produce for "sign message" requests. A contract account authorizes the same text through the [commitment verifier](#contract-account-payers). Lines are separated by `\n`, and there is no trailing newline:

```
x402 batch-settlement commitment
network: stellar:testnet
asset: <asset>
payTo: <payTo>
amount: <amount>
payer: <payer>
commitment: <commitment>
validUntil: <validUntil>
```

- `commitment` is 32 random bytes chosen by the buyer, unique per payment.
- `validUntil` is in Unix seconds.
- Every value is written exactly as it appears in the request.

### Verification rules

A commitment is valid when all of these hold:

1. Both `x402Version` fields are 2, and the scheme is `batch-settlement`.
2. The network is the one this gateway serves.
3. `accepted` equals `paymentRequirements`.
4. `payTo` is the ledger contract bound to the caller's seller deployment, and `asset` is its USDC.
5. `amount` is a positive integer.
6. The `payer` proves the text above: a classic `G...` account with `signature`, its SEP-53 signature, and a contract `C...` account with `authorizationEntry`, which the network must accept ([contract-account payers](#contract-account-payers)). A request carrying the other proof, or both, is refused as `invalid_payload`.
7. The `payer` is a buyer of the caller's seller deployment.
8. `validUntil` has not passed, and is at most `maxTimeoutSeconds` ahead.
9. The commitment has not been settled.
10. The buyer's available balance covers `amount` (`/verify`; `/settle` debits it atomically). On a vault, `/settle` also applies the buyer's daily spending limit and any exit the buyer requested, as every charge does; `/verify` does not, so a commitment it accepts can still be refused at settlement for those reasons.

### Contract-account payers

A contract account, such as a passkey smart wallet, has no key the gateway can check a signature with: only its own `__check_auth` interprets its credential, and only the network runs it. So the buyer authorizes the commitment as a call to a contract that does nothing else, and the gateway asks the network whether the account accepts it.

The **commitment verifier** is a stateless contract built from [`contracts/x402-verifier`](../../contracts/x402-verifier). Its one function, `commit(payer: Address, commitment: String)`, succeeds only with the payer's authorization of exactly that call. It holds nothing, changes nothing, has no admin and cannot be upgraded. `/supported` names it in `extra.commitmentVerifier`.

The buyer signs a `SorobanAuthorizationEntry`:

- credentials: address credentials for the `payer`, with a nonce of the wallet's choosing and a signature expiration ledger that covers the time until settlement;
- root invocation: the verifier's `commit`, with the `payer` and the [commitment text](#commitment-format) as a string, and no sub-invocations;
- signature: whatever the account's `__check_auth` takes, over the entry's standard signature payload, as for any Soroban authorization.

`authorizationEntry` is the signed entry's XDR in base64.

The gateway checks that the entry is for the `payer`, over exactly that call with this request's terms, and then simulates the call with the entry as its only authorization, in enforcing mode. The network runs the account's `__check_auth`: if it refuses, the commitment is refused as `invalid_batch_settlement_stellar_signature`, and an answer that does not reach the account, such as a missing verifier, is refused as an unexpected error rather than taken as consent. The call is never sent. Anyone who submits a signed entry on-chain only uses up the wallet's nonce, after which the network refuses the entry, so the commitment can no longer be settled.

The network is asked once for `/verify` and once more for a new `/settle`. A retry of a settled commitment is answered from its charge without asking it again, since the entry may have expired or the wallet changed its rules since; like a classic account's retry, it is not held to the commitment's window either. The rest of the request is still checked, the entry included, and a retry can never debit again.

Acceptance counts only if the simulated call consumed the entry, writing the payer's nonce: the network does that only once the call required the payer's authorization and the account accepted it. A contract configured as the verifier that does not require it therefore cannot stand in for a payer's consent; such a call is refused as an unexpected error.

The answer comes from a Stellar RPC node, so the node vouches for the payer's consent: a node that lied about a simulation could stand in for it, which no later on-chain step would catch, since the charge settles with the operator's authority. Run the gateway against a node you operate, and set `PAY_STELLAR_X402_WITNESS_RPC_URL` to a second node run by another provider: each authorization must then be accepted by both.

A wallet whose policies let some signers, such as session keys, call contracts that move no funds should not let them authorize the verifier: an authorization of `commit` spends the buyer's prepaid credit.

Configure the verifier built from this repository: check a deployment's code with `stellar contract info` against the Wasm hash of your build. The release image carries the build at `/usr/local/share/fermah-pay-stellar/fermah_pay_stellar_x402_verifier.wasm`. The worker, given the same `PAY_STELLAR_X402_VERIFIER_CONTRACT`, keeps its instance and code from being archived. On testnet, `fermah-pay-stellar-testnet deploy-x402-verifier --wasm <build>` deploys it at an address derived from the deployer and the Wasm's hash and records it in the profile.

### Storage

Settling a commitment stores a charge under the idempotency key `x402:<commitment>` and debits the buyer's available balance in the same database transaction. The `SettleResponse` carries:

- `transaction`: the commitment. It is the identifier this binding settles under, and it maps one to one to the charge.
- `extensions.prepaidLedger`: the charge (`chargeId`, `contractChargeId`, `state`, `outcome`), and `transactionHash` and `ledger` once its batch has landed.
- `extensions.prepaidLedger.replayed`: `true` when the commitment had already been settled.

### Double-spend prevention

- **In the gateway.** A commitment settles at most once per seller deployment: the same commitment again is answered with the same charge and debits nothing. The same commitment under other terms is refused as `invalid_batch_settlement_stellar_commitment_conflict`.
- **On-chain.** The charge's identifier is derived from the commitment, and the contract refuses an identifier it has already settled. A charge can therefore not be debited twice even if a batch is replayed.

### Commitment expiry

A commitment may be settled until `validUntil`. After that, a new commitment is refused as `invalid_batch_settlement_stellar_expired`, while a retry of one already settled is still answered with its charge. The charge itself has a settlement window on-chain (see [ledger API](ledger.md)). A charge that cannot be settled within that window is refunded to the buyer's available balance.

### Redemption

The settlement worker batches admitted charges, up to 98 per transaction, and submits them fee-bumped from the operator's accounts. No action is needed from the buyer or the resource server. `GET /settlements/{commitment}` reports the batch's transaction once it has landed.

### Trust model

The model is capital-backed: the buyer's USDC is deposited in advance, and each commitment draws on it.

- **Seller.** The seller is guaranteed that a settled commitment is paid from funds already deposited. The debit is final once the charge is `charged` on-chain.
- **Buyer.** The buyer is guaranteed that no commitment settles without its signature, or for a contract account its authorization as the gateway's RPC nodes report it, over the exact amount and seller, and that none settles twice. This bounds what a facilitator can take through this interface; the seller's API key can still charge through the [ledger API](ledger.md), within what the contract allows.
- **Custody.** Deposited USDC is held by the seller's treasury account, or on a vault by the contract itself; see the [prepaid ledger](../architecture/prepaid-contract.md) and [vault](../architecture/vault-contract.md) trust models.

## Reasons

| Reason | Meaning |
|---|---|
| `invalid_x402_version` | Not x402 v2 |
| `unsupported_scheme` | Not `batch-settlement` |
| `invalid_network` | Another network than the one served |
| `invalid_payment_requirements` | `accepted` differs from the requirements, `payTo` or `asset` is not the seller's, or the amount is not a positive integer |
| `invalid_payload` | A malformed body, payer, commitment, `validUntil`, signature or entry, or a proof that does not match the payer: `signature` for a classic account, `authorizationEntry` for a contract account, never both |
| `invalid_batch_settlement_stellar_signature` | The signature is not the payer's over these terms; for a contract account, the entry is not for these terms or the account refused it |
| `invalid_batch_settlement_stellar_unknown_payer` | The payer is not a buyer of this seller |
| `invalid_batch_settlement_stellar_expired` | Past `validUntil` |
| `invalid_batch_settlement_stellar_valid_until_too_far` | `validUntil` more than `maxTimeoutSeconds` ahead |
| `invalid_batch_settlement_stellar_commitment_used` | Already settled (`/verify`) |
| `invalid_batch_settlement_stellar_commitment_conflict` | Already settled under other terms (`/settle`) |
| `invalid_batch_settlement_stellar_ledger_not_configured` | The seller deployment has no ledger contract bound |
| `invalid_batch_settlement_stellar_contract_payer_unsupported` | The payer is a contract account and this gateway has no commitment verifier configured |
| `invalid_batch_settlement_stellar_above_spending_limit` | A vault: the charge would pass the buyer's daily spending limit (`/settle`) |
| `invalid_batch_settlement_stellar_exit_requested` | A vault: the charge would take credit an exit the buyer requested holds (`/settle`) |
| `insufficient_funds` | The buyer's available balance does not cover the amount |
| `unexpected_network_unavailable` | The network could not be read to admit a new charge or, for a contract account, to simulate its authorization; retry |
| `unexpected_verify_error`, `unexpected_settle_error` | An internal failure; retry |

## Conformance harness

`fermah-pay-stellar-x402-conformance` calls this interface the way a
third-party facilitator would: over HTTP, with nothing but the endpoint, the
seller deployment's API key and a buyer's key. It signs commitments as the
buyer, a classic account or, with `--buyer-contract`, a contract account
authorized by that key as [`contracts/example-account`](../../contracts/example-account)
is, and checks every answer against the protocol and this binding:

- `/supported` lists x402 v2 `batch-settlement` on the network, with
  `extensions` and `signers`;
- requests without an API key, or with an unknown one, are refused with HTTP
  401;
- each refusal above, from a request that differs from a valid one in one
  property: the amount or the commitment changed after signing, another
  `payTo`, another asset, `accepted` differing from the requirements,
  another network, x402 v1, the `exact` scheme, a malformed signature, an
  unknown payer, an expired or too distant `validUntil`, insufficient funds,
  and a body that does not parse; for a contract account, also an entry
  signed by a key the account does not hold and a classic account's
  signature in place of the entry;
- a valid commitment verifies, settles with the commitment as `transaction`
  and the charge in `extensions.prepaidLedger`, settles again as the same
  charge (`replayed`), is then refused by `/verify` as used, and under other
  terms is refused by `/settle` as a conflict;
- once `/settlements` reports the batch's transaction, an RPC node of the
  caller's choosing confirms it succeeded and that the contract's `charges`
  event charged the payer that amount under the charge's contract
  identifier.

```bash
export PAY_STELLAR_X402_API_KEY=fps_test_...
cargo run -q -p fermah-pay-stellar-cli --bin fermah-pay-stellar-x402-conformance -- \
  --endpoint https://facilitator.example --network stellar:testnet \
  --rpc-url https://soroban-testnet.stellar.org \
  --pay-to C...LEDGER --buyer-key-file buyer.secret --out x402-conformance.json
```

The buyer must be a buyer of the seller deployment with a small available
balance; the harness pays 0.005 USDC once. The record holds every request
and response (the API key is never written), the time each took, and a
verdict per case; the command exits non-zero if any case failed.

On testnet, `fermah-pay-stellar-testnet x402-conformance` runs the gateway
and the worker in process, deposits for a new buyer with no XLM, and runs
the same harness against it. The `testnet` workflow runs it, and the
evidence index lists its record.
